# Persistent authenticated alert receiver

This receiver accepts Alertmanager webhook notifications for one declared
monitoring source and a bounded alert/target allowlist. It persists sanitized
receipt identities in SQLite before acknowledging acceptance. The database is
independent of the monitored Gateway PostgreSQL and Redis services: a failure
of those dependencies must not remove the notification path.

The receiver implements the operational notification slice in roadmap Phase 6.
It does not operate the Gateway policy-event outbox or contact an incident
channel. A durable receipt proves delivery acceptance, not that a human read or
acted on the alert. Assign an operator for receiver storage, credential renewal,
retention and recovery, and a separate owner for staffed incident response.

## Authentication and accepted scope

Use a dedicated bearer token stored in a protected credential file. Require
HTTPS for remote delivery and keep certificate validation enabled. The supplied
[Alertmanager example](../../deploy/alertmanager.example.yaml) uses
`send_resolved: true`, disables redirects and environment proxies, and reads the
credential from a file. Replace its reserved hostname with the owned receiver.
Do not place a token in the URL, command line, Git, evidence or logs.

Authentication is checked before accepting or recording a request. A valid
bearer token establishes possession of that credential; it does not prove a
specific network origin or that the payload was generated by Prometheus.
Restrict access to the monitoring network, dedicate the credential to the chosen
Alertmanager deployment, and configure the exact permitted source/alert labels.
An authenticated notification outside that scope is still refused. Source
labels constrain authenticated content; they do not substitute for bearer
verification or network controls.

Treat the entire notification as untrusted. Validate bounded JSON and all alert
records before changing durable state. Do not use arbitrary `fingerprint`,
header values, annotations or message text as an authorization or deduplication
key. Unsupported or malformed messages and wrong credentials must add no
accepted receipts. Stored evidence contains only the reviewed labels, cycle
identity, status, timestamps and bounded aggregate/digest metadata; secrets and
raw alert bodies are not part of the receipt ledger.


## Start an owned receiver

The implementation uses Python 3.12 or later on a Unix platform and the standard
library. Native Windows startup is refused because the service requires Unix
file ownership and permissions. It has
no dependency on Gateway PostgreSQL or Redis. Run it as a dedicated unprivileged
service owner with an independently persistent local volume. A service manager
may restart the process, but must preserve the same volume, policy and protected
secret files. The supplied Linux drill starts and stops its own receiver; it
does not install a global service.

Create a new private directory and token as the intended service owner. These
example paths must be owned by that account; provision their parent directory
through the normal deployment process first:

```sh
umask 077
mkdir -m 0700 /var/lib/soup-wall-alerts
python3 - <<'TOKEN'
import os
import secrets
path = '/var/lib/soup-wall-alerts/receiver.token'
fd = os.open(path, os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
with os.fdopen(fd, 'w', encoding='ascii') as out:
    out.write(secrets.token_hex(32) + '\n')
    out.flush()
    os.fsync(out.fileno())
TOKEN
```

The token command refuses an existing file and never prints the secret. The
receiver requires an owned regular non-linked token file with no group/other
permissions (`0600`, or `0400` for a read-only mount) and 32–256 non-whitespace
ASCII token characters. Store the same token in the protected credential
file read by the selected Alertmanager, using the deployment secret manager or
an owned read-only secret mount. Do not copy it into public configuration.

Write `/var/lib/soup-wall-alerts/policy.json` with the exact selected values.
It must be an owned regular file, without symbolic/hard links or group/other
write permission; the accepted policy is bounded to 65,536 bytes.
This synthetic Docker example shows the three alerts accepted by the controlled
slice; production hostnames and accepted instances must be explicitly reviewed:

```json
{
  "receiver": "soup-wall-protected",
  "external_url": "http://alertmanager:9093",
  "sources": [
    {
      "job": "soup-wall-gateway",
      "instance": "gateway:8080",
      "alerts": [
        {"alertname": "LLMFirewallControlPlaneUnavailable", "severity": "critical", "component": "control-plane"},
        {"alertname": "LLMFirewallRedisLimitsUnavailable", "severity": "critical", "component": "admission-limits"},
        {"alertname": "LLMFirewallGatewayTargetDown", "severity": "critical", "component": "gateway"}
      ]
    }
  ],
  "optional_labels": {"environment": ["local"]}
}
```

Every alert must match the permitted `job`, `instance`, `alertname`, `severity`
and `component` tuple. Optional labels are allowed only with an enumerated
value; unexpected labels are refused. The configured Alertmanager `receiver`
and `externalURL` payload fields must match, too. Configure its route receiver
name and `--web.external-url` accordingly. Those payload fields are authenticated
content checks, not evidence of the actual peer's network identity. The example
HTTP `external_url` is metadata and is never fetched by the receiver; the webhook
transport below remains HTTPS.

Mount an operator-issued certificate for the receiver's hostname and a protected
private key. Start from the source checkout as the service owner:

```sh
python3 scripts/alert-receiver.py \
  --listen 0.0.0.0 --port 9081 \
  --data-dir /var/lib/soup-wall-alerts \
  --token-file /var/lib/soup-wall-alerts/receiver.token \
  --policy-file /var/lib/soup-wall-alerts/policy.json \
  --retention-days 30 --max-events 100000 \
  --tls-cert /run/secrets/receiver.crt \
  --tls-key /run/secrets/receiver.key
```

Bind only on the private monitoring network or behind its approved ingress.
Non-loopback plaintext is refused; `--tls-cert` and `--tls-key` must be supplied
together and TLS is at least version 1.2. HTTP without TLS is limited to an
explicit loopback endpoint for local fixtures. Clients must verify the receiver
hostname and certificate, using a scoped `ca_file` for an approved private CA.
Do not set `insecure_skip_verify` or add fixture CAs to global trust.

The default bind is `127.0.0.1:9081`. Read timeout defaults to five seconds
(accepted range 0.1–30 seconds); `--max-workers` defaults to eight and bounds
concurrent handlers (accepted range 1–8). Request bodies are limited to 65,536
bytes. Use normal monitoring-network connection and rate controls as well as
these service limits. A full worker pool replies HTTP 503 on plaintext
connections or closes a TLS connection before its handshake; both outcomes
require sender retry and add no accepted receipt.

The database is `<data-dir>/receipts.sqlite3`, with SQLite WAL and
`synchronous=FULL`. The directory must remain `0700`; the database and its
private companion state must remain owned and inaccessible to other users.
`POST /alerts` requires bearer authentication and a supported complete
Alertmanager v4 JSON message. `GET /receipts?limit=100` also requires bearer
authentication and returns sanitized durable receipts in first-acceptance order,
bounded to a limit of 1–1,000. `returned_records` and `has_more` declare whether
this bounded view covers the whole ledger; a truncated view is not a complete
receipt inventory. `GET /healthz` returns a fixed liveness response; it is not a
readiness, storage durability or successful-delivery assertion. Do not expose
the receipt endpoint outside the intended operator network.

Use the protected local token file to build authentication in memory when
inspecting receipts. This example avoids a token in process arguments; replace
the HTTPS URL and CA path with the approved receiver configuration:

```sh
python3 - <<'RECEIPTS'
import json
from pathlib import Path
import ssl
import urllib.request
class NoRedirect(urllib.request.HTTPRedirectHandler):
    def redirect_request(self, *_):
        return None
token = Path('/var/lib/soup-wall-alerts/receiver.token').read_text().strip()
context = ssl.create_default_context(cafile='/run/secrets/receiver-ca.crt')
client = urllib.request.build_opener(
    urllib.request.ProxyHandler({}), NoRedirect(),
    urllib.request.HTTPSHandler(context=context))
request = urllib.request.Request(
    'https://alerts.internal.example:9081/receipts?limit=100',
    headers={'Authorization': 'Bearer ' + token})
with client.open(request, timeout=5) as response:
    print(json.dumps(json.load(response), indent=2))
RECEIPTS
```

Receipt exports include `event_id`, `cycle_id`, approved `labels`, `status`,
`starts_at`, `ends_at`, first/last receipt times, duplicate counts and body
hash/change counters. They do not include the bearer token, annotations,
raw body or caller-supplied fingerprint. Body hashes are diagnostic metadata;
cycle identity is derived from the validated labels and canonical start time.

## Durability, correlation and retry

The authenticated alert identity uses its validated label set and `startsAt`.
Firing and resolved refer to the same cycle. Deduplication additionally includes
status, so a resolved transition is recorded once independently of the firing
transition. The state survives receiver restart; a replay after restart must
not create another accepted identity or effect within the retention window.
A later firing with a different `startsAt` starts a new cycle.

The receiver commits durable acceptance before returning success. Storage
failure or capacity exhaustion must return a retryable failure, never a success
that exists only in memory. Alertmanager may repeat a notification after a
lost response, receiver outage or restart. Delivery is at least once within
Alertmanager's configured persistence, retry and retention behavior; it does
not guarantee arrival or exactly-once incident handling. Back up the receiver
state if deduplication must survive host loss. Restoring an older backup can
reopen a previously recorded replay window.

Retention is an explicit deduplication horizon. The default is 30 days since
last receipt (configurable from 1 to 365 days), with 100,000 retained status
identities by default (configurable from 1 to 1,000,000). Expired receipts can be pruned;
a valid replay after that horizon can be recorded again. Select a horizon that
covers the Alertmanager retry/repeat window, outage recovery and backup policy.
Bound the number of retained identities as well as the incoming body size. A
full ledger returns HTTP 503 for new identities until retention frees capacity or an
operator expands the accepted limit; it must not silently evict live identities
to make acknowledgment succeed.

A resolved receipt without a retained firing receipt is not proof that firing
was delivered. Keep its outcome explicit for operator review: possible causes
include retention, a restored backup, configuration changes or missed initial
notification. Do not invent a firing receipt or relabel a resolved message as a
complete cycle.

## Ownership and recovery

Run one declared receiver instance with one owned private state directory.
Keep the database, SQLite journal/WAL files, credential and private TLS key
readable only by the service owner. The filesystem must support SQLite's local
locking and durability semantics; a shared network filesystem is not the
accepted storage model. The operator must monitor the host and durable disk
separately from the Gateway dependencies.

On receiver restart preserve the database and accepted source/alert
configuration. Keep the credential stable until a coordinated rotation; replacing
it only at the receiver causes Alertmanager retries to be rejected. Rotate the
receiver credential and Alertmanager credential file together, then prove both
firing and resolved delivery. Never weaken authentication to clear a backlog.

For a failed dependency notification path:

1. Check receiver process health, TLS name/trust, protected credential access,
   storage writeability and capacity without printing secret values.
2. Restore the receiver with its original durable database and accepted scope.
   Keep Alertmanager's persistent data so pending notifications can resume.
3. Check authenticated receipts for the same label identity and `startsAt`.
   Repeated delivery should change duplicate metadata, not add another identity.
4. Restore the dependency through the approved deployment control plane and
   verify readiness, useful Gateway behavior and a matching resolved receipt.
5. Preserve failed/incomplete and recovery evidence with source/configuration
   hashes. Record any lost or pruned receipt window rather than claiming it was
   continuously observed.

Do not delete production receipts or stop unrelated services during a drill.
Receipt persistence is not a replacement for Alertmanager persistence,
notification routing or a staffed critical-alert policy.

## Verification boundary

Use the [current-source Linux monitoring procedure](LOCAL_MONITORING_ACCEPTANCE.md#current-source-linux-dependency-and-receiver-recovery)
for a disposable Gateway/PostgreSQL/Redis/Prometheus/Alertmanager slice. It
exercises actual dependency and Gateway faults, authenticated firing/resolved
receipt correlation, receiver outage/restart, retry, duplicate replay, refused
credentials/targets and owned cleanup. HTTPS uses a per-run certificate and
explicit CA trust without changing the host trust store.

Free focused regressions run without Docker or external incident channels:

```sh
python3 -m unittest discover -s scripts/tests -p 'test_*alert*.py' -v
```

A passing controlled fixture covers its declared Linux source and configuration.
It is not evidence of a deployed public receiver, managed-service failover,
certificate rotation, external notification delivery or human response.
